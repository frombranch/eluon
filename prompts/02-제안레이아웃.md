# 프롬프트 02 — 제안 단계에서 몽타주 쓰기

제안서에 붙일 화면 이미지는 "그럴듯한 목업"이 아니라 **실제로 구현 가능한 컴포넌트로 조립된 화면**이어야
기술협상 단계에서 말이 바뀌지 않습니다. 몽타주는 그 근거가 됩니다.

---

## A. RFP 요구사항 → 자산 매핑표

```
첨부한 RFP(또는 요구사항 정의서)를 읽고, Eluon로 얼마나 커버되는지 판단해줘.

라이브러리: https://github.com/frombranch/eluon (CLAUDE.md, manifest.json 먼저 읽기)

표로 정리해줘.
| RFP 요구사항 | 필요한 화면/기능 | 커버하는 자산 ID | 커버 상태 | 비고 |
커버 상태는 셋 중 하나: 그대로 사용 / 변형 필요 / 신규 제작

마지막에 요약해줘.
- 그대로 사용 가능한 비율(%)
- 신규 제작이 필요한 항목 수와, 그중 공수가 큰 것 3개
```

**쓰임:** 견적 근거, 일정 산정, "우리는 이미 이만큼 갖고 있습니다"라는 제안 논거.

## B. 제안용 화면 시안 3안

```
<프로젝트명> 제안용으로 <메인 화면> 시안을 3안으로 만들어줘.
세 안 모두 manifest의 자산과 specByTheme.<테마> 를 지키되, 아래 축만 다르게 가져가.

1안 — 정보 밀도 높은 안 (한 화면에 많이)
2안 — 여백 넓은 브랜드 강조 안
3안 — 모바일 우선 안

각 안마다: 사용한 자산 ID 목록 / 이 안이 RFP의 어떤 요구를 겨냥하는지 한 줄 / 리스크 한 줄
```

## C. 고객사 톤에 맞춘 변형 제안

```
Eluon는 그대로 두고, 고객사 브랜드에 맞춘 "토큰 오버라이드"만 제안해줘.
컴포넌트 구조는 건드리지 않는다는 전제야.

- 첨부: 고객사 BI 가이드 / 기존 사이트 캡처
- 산출: tokens 오버라이드 표 (토큰명 / 우리 기본값 / 고객사 제안값 / 근거)
- 대비비 4.5:1을 못 넘는 조합은 반드시 표시하고 대안을 함께 제시
```

## 제안 문서에 넣을 때

몽타주 시트(index/sheet-eluo.png) 자체를 제안서 한 페이지로 넣는 것이 효과가 좋습니다.
"저희는 이 화면을 처음부터 그리지 않습니다. 검증된 컴포넌트 N개를 조립합니다"가
한 장으로 설명됩니다. `index/sheet-eluo.png`을 그대로 쓰면 됩니다.
