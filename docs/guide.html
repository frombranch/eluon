Eluon 사용설명서

디자인 시스템을 코드로 만들고, GitHub에 올리고, 자산 파일로 바꿔서, 빌더로 프롬프트를 뽑기까지. 각 단계에서 무엇이 무엇을 만드는지와, 빌더 화면의 설정이 각각 무엇을 바꾸는지를 적었습니다.

왜 이렇게 만들었나

보통의 UI 킷은 피그마 파일과 이미지를 줍니다. 그러면 이미지와 규격이 따로 놉니다. 버튼 높이를 56에서 52로 바꾸려면 피그마에서 다시 뽑고, 이미지 파일을 갈아끼우고, 문서의 숫자도 고쳐야 합니다. 셋 중 하나만 빠뜨리면 어긋납니다.

Eluon은 규격을 코드에 적으면 이미지가 나옵니다. 한 곳을 고치면 CSS·PNG·문서가 같이 바뀝니다. 어긋날 방법이 없습니다.

그리고 이 시스템의 진짜 독자는 사람이 아니라 AI 에이전트입니다. 그래서 각 자산에 규격뿐 아니라 언제 쓰는지(usage)와 언제 쓰면 안 되는지(dont)가 같이 적혀 있습니다. 에이전트가 고를 근거가 되라고 넣은 것입니다.

사람이 고치는 파일은 둘뿐입니다 tokens/(색·라운드·타이포) 와 recipes/components.py(컴포넌트 정의).

manifest.json·docs/·index/·모든 PNG는 생성물입니다. 손으로 고치면 다음 빌드에 되돌아갑니다.

테마 = 그 고객의 데이터

우리는 대행사입니다. 작업 기준은 고객 데이터여야 합니다. 그래서 테마는 색만이 아니라 색 · 라운드 · 크기를 갖습니다. 같은 btn-primary-lg라도 고객사마다 높이와 패딩이 다르게 렌더됩니다.

그래서 spec 읽는 법이 바뀌었습니다 v1.1.0

치수가 테마마다 다르므로, manifest.json의 spec은 토큰 이름만 말하고 실제 수치는 specByTheme에 테마별로 들어 있습니다.

"spec": { "height": "control.lg.height", "paddingX": "control.lg.paddingX" }

"specByTheme": {
  "eluo":  { "height": 56, "paddingX": 24 },
  "atlas": { "height": 56, "paddingX": 24 },
  "ember": { "height": 52, "paddingX": 44 }    ← 고객사 실측
}
테마를 모르면 규격도 모릅니다 "버튼 높이가 몇이냐"에 테마 없이는 답할 수 없습니다. 그래서 일관성 QA 절차의 1단계가 테마 확정입니다. (QA는 빌더 버튼에서는 빠졌습니다 — 절차는 CLAUDE.md §4에 그대로 있어 에이전트에게 직접 시킵니다.) 대조할 기준은 spec이 아니라 specByTheme.<테마>입니다.

빌더도 마찬가지입니다 — 자산을 미리 지정하면 고른 테마의 수치가 프롬프트에 실립니다.

고객사에 있는 축이 우리에게 없으면, 토큰을 늘립니다 v1.1.1

탭이 실제 사례입니다. 같은 간격처럼 보여도 간격을 만드는 방식이 달랐습니다.

Eluon 기본   항목 패딩 없음 · gap 28 로 벌림
원본         항목마다 좌우 22 · 항목끼리는 붙임 (gap 0)

gap만 0으로 맞추면 라벨이 서로 붙어버립니다. "항목 좌우 패딩"이라는 축이 Eluon에 아예 없었기 때문입니다. 그래서 tab.itemPaddingX 토큰을 새로 만들고 기본값을 0으로 뒀습니다 — 기본이 0이라 기존 테마 렌더는 한 픽셀도 안 바뀝니다.

고객사 값이 안 들어가면 값을 구부리지 말고 축을 늘리십시오 비슷한 숫자로 억지로 맞추면 그때는 비슷해 보여도 다음 화면에서 어긋납니다. 새 토큰의 기본값을 0이나 현재 값으로 두면 기존 테마는 그대로이고 그 고객사만 달라집니다.

테마로는 못 바꾸는 것 — 구조

크기까지 테마가 갖게 됐지만, 구조는 여전히 수치가 아닙니다. atlas 테마 파일에 실제 사례가 적혀 있습니다.

원본의 주요 버튼은 흰 배경 + 검정 1px 테두리인데 Eluon의 btn-primary는 채움형입니다. 채움이냐 테두리냐는 토큰으로 안 담깁니다. 이럴 때는 btn-outline-lg 같은 다른 자산을 쓰거나 새 컴포넌트를 만듭니다.

값은 피그마에서도, 웹사이트에서도 뽑습니다

고객사 피그마를 못 받았어도 공개 웹사이트가 있으면 거기서 뽑습니다. 브라우저가 계산한 값은 설계값이 아니라 실제로 그려진 값이라, 오히려 정확한 축도 있습니다. harbor가 그렇게 만든 테마입니다.

뷰포트 비례 사이트는 기준 폭을 정하고 환산해야 합니다 harbor의 원본이 그랬습니다 — html { font-size: calc(0px + 0.520833vw) }라 화면 폭에 따라 모든 수치가 연속으로 변합니다. 측정 창이 1038px이라 루트가 6.24px로 잡혀 처음엔 폰트가 6.24px로 나왔습니다. 1920 기준으로 환산해서야 제 값이 됐습니다.

그리고 리뉴얼 제안이면 현재 사이트는 바꿀 대상이지 따를 기준이 아닐 수 있습니다. 기준으로 삼기 전에 확인하십시오.

원본을 그대로 옮기지 않는 경우가 있습니다 — 접근성 harbor 원본의 연한 회색 #999999는 흰 배경 대비 2.85:1로 본문 기준(4.5)뿐 아니라 UI 경계 기준(3.0)도 못 넘깁니다. 그대로 넣지 않고 text.tertiary는 #666666, border.default는 3:1을 넘는 가장 밝은 값 #939393을 넣었습니다. 무엇을 왜 바꿨는지는 테마 파일의 $measured에 적습니다.

실측 기록이 없는 축은 비워 둡니다

고객사 원본에 대응 요소가 없으면 지어내지 않고 core 기본값을 씁니다. 무엇을 옮겼고 무엇을 안 옮겼는지는 각 테마 파일의 $measured에 적습니다. ember는 입력 필드·모달·토스트·테이블에, harbor는 카드·입력 필드·테이블 등에 원본이 없어 기본값을 쓰고 있습니다.

기본값을 실측으로 오해하지 마십시오 specByTheme는 실측값이든 기본값이든 똑같이 숫자로 보입니다. 어느 쪽인지는 테마 파일의 $measured에만 적혀 있습니다.

지금 atlas가 그 상태입니다 — 색·라운드·카드 폭은 고객사 값이지만 버튼 높이·패딩·칩·배지·탭은 Eluon 기본값입니다. 정확한 재현이 필요한 작업이면 원본 실측이 먼저입니다.

가명은 이름과 색이 다릅니다 고객사 테마의 id는 고객사를 특정할 수 없게 지은 가명입니다. ember는 잉걸불이라는 뜻이지만 실제 색은 딥그린입니다. 브랜드색은 이름으로 짐작하지 말고 언제나 --color-brand-primary에서 읽으십시오. 어느 고객사인지는 저장소가 아니라 로컬 private 노트에 있습니다.

활자에는 "어디에 쓰는지"가 붙었습니다

수치만 있고 역할이 없으면 제목과 본문이 다 비슷한 크기로 나옵니다. 이제 스타일마다 자리를 적어 둡니다.

"display1":  { "size":40, ..., "role": "페이지 제목 · 히어로. 한 화면에 하나만 씁니다." }

크기를 숫자로 쓰지 않습니다. var(--type-heading1-size), 또는 한 줄 축약형 font:var(--type-heading1)을 씁니다.

둘 다 manifest.json의 foundationByTheme.<테마>에 실려 나갑니다 — 폰트·활자·레이아웃·간격·그림자·브레이크포인트가 한 덩어리입니다. 빌더가 만드는 프롬프트에도 레이아웃 절과 활자 절이 따로 붙습니다.

라운드 눈금은 둘입니다 v1.7.1 sm·md·lg는 컨트롤(버튼·입력·칩), xl은 컨테이너(카드·표·모달·토스트)입니다.

섞으면 사고가 납니다. 알약 버튼을 쓰는 테마는 sm/md/lg가 전부 999px이라, lg를 쓰던 표와 토스트까지 알약이 됐습니다. 표가 알약일 리는 없습니다. build_manifest.py가 이제 검사합니다.

상태는 자산이 아닙니다 v1.9.0

목록에 btn-primary-lg-disabled, input-text-md-error 같은 항목이 자산처럼 섞여 있었습니다. 다섯 개 다 규격은 부모와 같고 토큰만 다릅니다. 자산이 아니라 상태 그림입니다.

지우지 않고 부모에 접었습니다. 지우면 "에러일 때 테두리가 danger"를 다시 알 방법이 없고, 이미 배포된 태그에서 그 ID를 참조할 수도 있습니다.

                 "tokens":{ "border":"border.danger", "helper":"danger.text" }}]

어디어떻게 됩니다
자산 수상태 5개는 따로 셉니다 — 목록 수에 넣지 않습니다
몽타주 시트빠집니다 — "이 중에 골라줘"용이라 고르는 물건만

테마

고른 테마가 프롬프트 두 곳에 들어갑니다. 테마: eluo 한 줄과, 불러올 토큰 CSS 주소입니다. 시스템 주소는 테마와 무관하게 늘 Eluon을 가리킵니다 — 컴포넌트는 저장소에서 오고 테마는 색만 갈아끼우기 때문입니다.

안 쓰는 테마 숨기기

저장소가 바뀌는 것이 아닙니다 이 페이지는 GitHub Pages에서 읽기 전용으로 돕니다. ×는 이 브라우저 목록에서만 감추는 것이고 tokens/theme-*.json은 그대로 있습니다. 아래 숨긴 테마 N개 — 다시 보이기로 언제든 되돌립니다.

저장소에서 진짜 지우려면 eluon.config.json의 themes에서 빼고 파이프라인을 돌려야 합니다.

v1.7.0 전에는 레이아웃과 활자가 manifest에 없었습니다. 폭·그리드·섹션 여백도, 어느 자리에 어떤 활자를 쓸지도 시스템이 말해주지 않아 매번 새로 정했습니다. 지금은 foundationByTheme.<테마>에 실리고 프롬프트에 레이아웃 절과 활자 절이 붙습니다. 그래도 허전하면 헤더·히어로·푸터를 자산으로 쓰고 있는지 보십시오 — v1.8.0에 생겼습니다.
한글이 이상한 데서 끊깁니다
word-break: keep-all과 overflow-wrap: anywhere를 짝으로 걸었는지 보십시오. 하나만 걸면 한쪽이 깨집니다. <br>로 줄을 나눴다면 그것부터 빼십시오 — 폭이 바뀌면 엉뚱한 자리에서 끊깁니다. v1.10.0부터 프롬프트가 이걸 지시합니다.
에러·포커스 색이 매번 다릅니다
상태를 안 알려주면 지어냅니다. v1.9.0부터 자산을 미리 지정하면 error — border → border.danger처럼 무엇이 달라지는지가 프롬프트에 실립니다. 상태는 따로 고르는 자산이 아니니 목록에서 찾지 마십시오.
빌더 탭이 눌리지 않습니다
자산 파일이 아직 안 붙었다는 뜻입니다. 탭 오른쪽에 이유가 적혀 있습니다. 피그마 자산 탭에서 먼저 연결하십시오.
자산 수가 적게 보입니다 36개여야 정상
낡은 자산 파일을 보고 있는 것입니다. 옛 파일에는 커머스 5종과 section-header-md가 없어서, 있는 자산을 없다고 잘못 판단하게 됩니다. 소스 바의 버전을 확인하십시오.
시안의 색이 다 빠져 나옵니다
아티팩트로 발행했는데 작업 유형을 시안 제작으로 골랐을 가능성이 큽니다. 아티팩트는 외부 파일을 못 읽으므로 아티팩트 발행을 골라야 CSS 인라인 지시가 들어갑니다.
자산을 추가했는데 빌더에 안 뜹니다
build_pb_manifest.py를 안 돌렸습니다. manifest만 갱신하면 빌더용 변환본이 낡은 채로 남습니다. CI가 --check로 막지만 로컬에서는 그냥 지나갑니다.
버튼 높이가 문서와 다릅니다
v1.1.0부터 치수가 테마마다 다릅니다. spec의 control.lg.height는 토큰 이름이고 실제 px는 specByTheme.<테마>에 있습니다. 어느 테마로 보고 있는지부터 확인하십시오.
시안이 모바일에서 깨집니다
v1.4.0부터 반응형이 자산 계약에 들어갔습니다. 프롬프트에 자산별 접기 규칙이 실리고 QA가 responsiveByTheme와 375px 가로 넘침을 대조합니다. 그전에 뽑은 시안이면 다시 뽑으십시오.
CDN 이미지가 옛것으로 나옵니다
jsDelivr가 태그 주소를 길게 캐싱합니다. 버전을 올려 새 태그를 밀어야 실제로 교체됩니다. 그래서 @main을 쓰지 않습니다.
